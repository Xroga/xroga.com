# Founder access and diagnostics boundary

The founder shell at `/os-preview/founder` is not a hidden-link gate. Middleware treats it as protected, and the server page independently uses `supabase.auth.getUser()`, checks a confirmed normalized `hello@xroga.com` email, requires `current_community_role()` to be `owner`, and requires Supabase MFA `currentLevel === 'aal2'`. Any missing or failed check denies access. No localStorage, query token, public environment secret or client email check authorizes it. Guest middleware redirects to sign-in; other denials redirect to a neutral access-denied route. The page is dynamic, `no-store`, and `noindex`.

The existing `/admin` page and backend `adminMiddleware` allow both `admin` and `owner`. The existing `/api/admin/errors` and `/api/operations/readiness` have **not** been proven founder-exclusive. Command 1 deliberately does not call either, does not alter broad admin permissions, and does not serialize logs into the founder page. Before a future adapter is attached, backend authorization must enforce founder identity/owner/AAL2 on **each data endpoint** with tenant scoping, redaction, bounded pagination and auditable access. Endpoint policy cannot rely on this page gate.

Future diagnostic records may include time, severity, environment, correlation ID, sanitized summary, impact, retry status, owner and next action. They must not include tokens, credentials, raw customer prompts, cross-tenant data or unredacted traces. Frontend error boundaries show generic language; server-side logging should follow existing safe conventions without sending sensitive messages to a public client.
