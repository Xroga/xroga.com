# Repository execution: audit and plan (18 November 2026)

Status: audit only. Nothing in this file is implemented or tested. Cloud Run (or Cloudflare) only; no Fly.

## What exists
- `backend/src/sandbox/`: provider-neutral isolation seam (`sandboxProviders.ts`, `sandboxTypes.ts`), metering (`meteredExecution.ts`), cleanup (`google/orphanReconciler.ts`).
- `remoteSandbox.ts`: HTTP contract for a remote isolation worker, inert unless `XROGA_SANDBOX_WORKER_URL` is set. Worker serves `GET /health` -> `{ready:true, networkIsolation:true}` and `POST /execute` taking `{files, command, args, timeoutMs, networkPolicy, environment, limits, image?}` and returning `{exitCode, stdout, stderr, timedOut, killedForLimit, durationMs}`. Header bearer token; https or loopback only.
- `deploy/browser-worker/container-spec.json` + `workers/containerSpec.ts`: reviewed hardening checker (non-root, read-only rootfs, caps dropped, seccomp, internal network + egress proxy, deny CIDRs).
- Staging Cloud Run has no sandbox variables set, so every provider probe fails and execution is refused (by design: no fallback to the API host).

## Hard limits found in the existing design
- `registry-only` network policy is refused until a verified restricted-network worker exists. Only `none` (offline) is admitted, and only by a worker that can really deny the network.
- A Python or Node project that needs `pip` or `npm` dependencies, or needs the internet (job boards, maps, lead sources), therefore cannot run today.

## Smallest build that fits
1. A Cloud Run service `xroga-sandbox-worker` implementing the contract above: one request per instance (concurrency 1), per-request temp directory removed afterwards, exact environment only, output and file caps, timeout and process limits, bearer token, IAM invoker limited to the API service account, a service account with no roles, min instances 0.
2. Network: a VPC with deny-all egress for the offline mode (verified by a probe that tries to connect out and must fail); a second, separately reviewed worker or egress proxy with a package-registry and approved-host allowlist for dependency install and permitted data sources.
3. Retrieval stage on the trusted side: fetch the repository tarball at a pinned commit SHA over the existing bounded public reader, install wheels only (`pip download --only-binary=:all:`), then execute offline.
4. One extension tool and one backend route under the existing run ID (same ledger, checkpoints, approvals); results returned as files through the existing artifact store; Experience Engine records only verified procedures.
5. Independent security review of the worker, the egress allowlist and the retrieval stage before untrusted repositories are enabled.

## Source-use caveats recorded for the examples
- JobSpy (MIT) scrapes LinkedIn, Indeed and others and offers proxy rotation to bypass blocking; those sources' terms and access controls apply regardless of the licence. Permitted sources (official or public job APIs) should be preferred.
- Google Maps scraping likewise needs its terms checked; an authorised source is the fallback.

### Stage 3: restricted-network stage (verified on the real worker; no paid infrastructure)
Design (all in `deploy/sandbox-worker/`): the sandbox keeps NO network interface except loopback. A bridge inside its namespace exposes a unix socket as 127.0.0.1:3128; the other end is an allowlisting CONNECT proxy inside the worker process, alive only for the stage that asked. Policy: CONNECT only, port 443 only, exact host names from the allowlist (`pypi.org`, `files.pythonhosted.org`, `registry.npmjs.org`, plus names the operator sets in `XROGA_WORKER_ALLOWED_HOSTS`; a request can never add one); DNS is resolved by the proxy and the host is refused if any answer is private, loopback, link-local, metadata or non-global, and the checked address is the one dialled; bounded tunnels, bytes and idle time; no secrets enter the stage (the environment is exactly the caller's plus proxy variables). The Cloud Run service is unchanged apart from its image and timeout (no VPC, no NAT, no firewall rule, no proxy product). Backend: `RemoteSandboxRuntime` accepts `registry-only` only with `XROGA_SANDBOX_WORKER_RESTRICTED=1` AND a fresh `restrictedNetwork === true` from the worker's own self-test; otherwise it sends nothing.
- Verification with a positive control (`restricted-selftest-20261118.json`, from inside a restricted-stage sandbox on the deployed worker): a real TLS request to `pypi.org` through the proxy returned 200/200; `example.com`, `metadata.google.internal` and `pypi.org:80` were refused (403, 403, 403); a direct connection to `1.1.1.1:443` was BLOCKED; 2 visible processes; the worker token not readable. The worker offers the stage only after this passes, on every new container.
- End to end (`repo-change-staging-network-run-20261118.json`): same pinned repo; the edit adds `requirements.txt` (`pytest==8.3.3`) and a test. The edited copy was planned from its own files: stage 1 `pip install` through the proxy (4.5 s), stage 2 `pytest` offline in the same container, 664 passed, 1 skipped. Verdict `verified`; total 20 s.
- Unit tests: `egress.test.mjs` (address classification, allowlist parsing, policy table including rebinding to the metadata address, port 80, sub-domains, userinfo tricks, tunnel cap, non-CONNECT), `server.test.mjs`, `remoteRestricted.test.ts`, `workerExecutionPort.test.ts`.
- Not enabled for users: the staging API has no `XROGA_SANDBOX_WORKER_RESTRICTED`; the backend code is not deployed; npm install has not been exercised on the real worker (only pip); the proxy sees host names and byte counts, not content.

### Residual risks the independent security review must cover (not signed here)
1. Escape from the user, PID, mount and network namespaces of an unprivileged process (kernel and gVisor surface); the job shares the worker's filesystem and the worker's kernel user.
2. The proxy: host canonicalisation (case, trailing dot, IDN, `host:port@host`), DNS rebinding (resolved once and dialled by address), IPv6 and mapped addresses, request smuggling inside CONNECT, tunnel and byte limits, behaviour when the allowlist is extended through `XROGA_WORKER_ALLOWED_HOSTS`.
3. Exfiltration through an allowed host: a job can still send data to `pypi.org` or `registry.npmjs.org` (for example by uploading a package or a crafted request path); the stage has no secrets, but a user's repository content could be sent out. Decide whether that is acceptable for private source (the retrieval path currently serves public repositories only).
4. Supply chain: packages from allowed registries run as untrusted code inside the sandbox (sdists execute `setup.py`); `--ignore-scripts` applies to npm only; no hash pinning, no wheels-only mode.
5. The shared worker token (a plain environment variable on the Cloud Run service; Secret Manager is the better home), the IAM invoker list, and Cloud Run's 900 s service timeout versus the 800 s stage budget.
6. Resource limits are prlimit plus wall clock, not cgroups; a fork or memory bomb is bounded per request, not per tenant.
7. The metering ledger: record-only by default, cap behaviour under a ledger outage, and the settlement of a run killed by the platform (the sweep charges the hold in full after two hours).

### Controlled acquisition (`backend/src/sandbox/dependencyAcquisition.ts`, 5 tests)
Trusted-side planning before anything is fetched in the sandbox:
- Exact pins only. A range, tag, partial version or odd package name is refused (`UNPINNED`); a version the registry does not list is refused.
- pip: every published wheel sha256 for the version is written into a lock file and installed with `--require-hashes --only-binary=:all:`, so pip itself refuses an unhashed requirement (every transitive one too) and any source build (no `setup.py` runs).
- npm: the registry sha512 integrity is recorded; installs use `--ignore-scripts`; an OFFLINE verify stage compares the integrity npm recorded for each pinned package with the digest read on the trusted side (exit 3 on mismatch). Transitive npm packages are covered by the registry's own integrity unless the repository supplies a lock file (`npm ci`, which enforces it).
- Licence review: each package's declared licence is classed permissive, review or unknown. Copyleft, "see licence" and undeclared licences make the plan NOT ready until acknowledged by name.
- Install runs only behind the egress allowlist (no metadata service, no credentials, nothing from the host); everything after it is offline; a fresh container per request.

### Security finding fixed (automated review, 18 November 2026): PATH hijack of the worker's own launchers
Finding: the worker built the job's PATH with run-local directories (`.local/bin`, `.xroga-deps/node_modules/.bin`, `node_modules/.bin`) FIRST and spawned `unshare`, `prlimit` and `sh` by bare name, so a repository file planted at `.local/bin/unshare` would have run outside the sandbox with the worker's privileges (the worker's token lives in its memory). Valid. Fix: the launchers are resolved once from the worker's own PATH and spawned by absolute path; run-local directories are appended AFTER the system PATH (so they can add commands but never shadow one); the restricted-stage entry script finds its helpers on the system path only and restores the job PATH just before the job starts. Verified on the deployed worker (revision xroga-sandbox-worker-00011-tak): with planted `unshare`, `prlimit` and `sh` in `.local/bin`, both an offline and a restricted-network run resolved the system binaries (`/usr/bin/unshare`, `/usr/bin/sh`); the restricted self-test still passes (positive control 200/200, off-list refused, direct blocked); the yamllint CLI still runs from the run-local bin directory. A unit test covers shadowing on Linux (skipped on Windows). Not covered: a job can still run anything it likes INSIDE the sandbox, which is the isolation model; the independent review should still check argument and environment handling of the other spawn calls.
