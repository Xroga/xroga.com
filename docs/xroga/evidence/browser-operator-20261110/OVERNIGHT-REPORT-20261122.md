## Round 9 (2026-11-22 afternoon): features taken from the Codex browser recordings
Source of the ideas: the owner's two screen recordings of the Codex desktop browser agent drafting 50 + 50 emails (see the memory note; frames sampled every 5 s). Replica results only: the test webmail is `fixtures/pages/apps/adv-mail.html` (a replica with the quirks seen in the recordings: paragraph breaks squeezed unless a box is ticked, a draft that is only autosaved is lost when the editor closes, a Delete button over a row's middle on hover, the same recipient saved twice makes two drafts). The server's state is the grade.

- **Batch list with verified-only counts** (`agent/task-plan.ts`, `agent/loop.ts`): `plan` gained `items` and `mark`. Items are short unique names (duplicates refused); `saved` records the page-load count; `verified` is refused unless the item was saved, a page has loaded since (reload or reopen), and `check {text}` is visible on the page now. `done` with outcome success is refused while an item is not verified (twice, then the run ends as partial with the counts appended). The list is stored in the plan snapshot, so a restarted run reads it and continues without repeating items. 8 unit tests plus 4 loop tests. **Not adopted by the model in any live run**: in 11 webmail runs DeepSeek used milestones but never `items` or `mark`, so the live benefit is unproven; it is tested at unit level only.
- **Reload-persistence check**: delivered as the load-gated `verified` rule above, not as an automatic reload after a save (an automatic reload would drop an open editor and is meaningless in many apps).
- **Hover-revealed controls** (`core/tools/act.ts`, `core/interaction/actionability.ts`): for a row, card or clickable block, the pointer hovers first and, when a separate control (a row's Delete or Archive button) now covers the click point, or the pointer already rests there and the click was about to be refused, the click goes to another point of the element clear of it and the result says so. Chromium scenario `S3-click-clear-of-hover-controls` (row opens, nothing deleted). Not exercised in a live-model run (the model reopened drafts by ref and was never blocked).
- **Repeated sequences become one batch** (`agent/repeat-detector.ts`, wired in `agent/loop.ts`; prompt line): when the same 2-6 step sequence has been done three times, one advisory says the rest can go in one `batch`. `batch` steps can carry `keep: true` so reads in the middle return their text (cut to 1,500 characters each, 9,000 in all), which lets ten items be checked in one call. 4 + 3 unit tests.
- **Harness finding (important):** the eval harness never offered the `batch` tool, although the product does (`checks/eval.ts`: only `plan` was added). Every earlier eval therefore measured the model without batch. It is now offered by default (`batch:false` restores the old setting). Earlier cross-round comparisons in this report are between like-for-like runs, but they underused batch.

## Round 11 (2026-11-22 night): one identity for an action, and what the panel does with late events
Evidence labels as above. Source: the video directive's section 4 (one synchronized action ledger) and the owner's clarifications.

**Built (code, with tests):**
- **Action identity** (`ui/protocol.ts` `ToolRow`, `agent/loop.ts`, `browser-control/protocol/results.ts`): every row event the loop sends now carries `actionId` (`runId:callId`), a `seq` that rises with every event of the run, the tab it ran on and the page revision (`epoch`) it was decided on. The layer's receipt that is stored in the conversation carries the same `actionId`. So the model's call, the panel row and the stored receipt name one action. `UNIT_ONLY` (loop test with a fake layer: ids equal, sequence strictly rising and unique, tab and revision present, stored receipt stamped).
- **The panel no longer lets a late or replayed event undo a result** (`side-panel/state.ts` `mayApplyRow`): an event with a lower or equal `seq` than the row shown is ignored; a finished action (done, failed, skipped) never goes back to running; a replayed end event leaves one row. This was a real defect: the old reducer merged any later event over the row, so a "running" update arriving after "done" (after a reconnect or a replay) reverted a finished action. `UNIT_ONLY` (reducer tests, with and without sequences; rows stored before this keep the old merge except that a finished row is never reopened).
- **Prompt:** one clause added to the no-limits paragraph: never ask for an integration or a new login for what an open signed-in tab already shows; operate the tab. (It is a prompt change, not an engineering result, and the owner asked for engineering; it states a policy the code already follows.) Two context-budget tests that are tuned to the prompt's size needed their synthetic limit raised from 6,900 to 7,000, as the repository's own comment prescribes.

**Checked, not changed:** competing mutations in one reply are already serialised by the loop (consecutive reads run together; each mutation waits for the last, and a later call is skipped when the earlier diff removed its target or changed the page), so two calls cannot mutate one tab at once. ## Round 12 (2026-11-22 night): measuring wasted turns, and removing their largest cause
Source: the owner's directive on excessive unproductive turns. The method: measure first (which calls produce nothing), fix the cause in the execution layer, then compare matched runs. No turn cap was added.

**Measurement tool (new):** `live/waste-report.mjs` reads any eval results and classifies every call as WORK (changed the page), LOOK (snapshot, read, find, screenshot, wait), LOOK* (the third look in a row with nothing done between), NOOP (an action with no effect), ERROR or REPEAT (the same tool on the same target twice). On the 13-task regression of round 11 (137 calls): WORK 75, LOOK 39, NOOP 11, LOOK* 5, REPEAT 3, ERROR 1. All 13 DOM-based replica tasks (CRM, ads draft, database, shop, order, documents, calendar, webmail) wasted 0-4% of their calls; the three painted-canvas tasks (canvas-menu, painted-menu-4, timeline-split) wasted 50-60%. So the wasted turns of this corpus were one class: **aiming at things drawn on a canvas by reading a picture** (misreading which label is which, clicking, taking three or four more pictures to see what happened). ## Round 16 (2026-11-23): unfamiliar-form holdouts, and a fixture bug that looked like an agent weakness
Live DeepSeek (effort high) on existing unfamiliar-form replica tasks (`hard-form`, `app-settings`, `app-novel`, `app-crm`, 3 layout variants each; `live-model/holdout-forms-r15.jsonl`): 9 of 10 graded passes, mean 13.5 turns, 78 s. `app-settings-1..3` took 25, 25, 25 turns (117 to 209 s) and one failed. ## Round 19 (2026-11-23 night): broad regression, and computing instead of reasoning
**Broad live regression (DeepSeek, everything from rounds 13 to 18 on, adaptive effort, cap 40; `live-model/regression-r18.jsonl`):** 24 of 25 replica tasks passed; median 23 s, mean 34 s, mean 9.6 turns.
