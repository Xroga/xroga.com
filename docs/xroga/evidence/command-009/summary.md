# Command 009 software evidence

All enabled new OAuth, provider-key and project-runtime secret writers use the canonical version 3 CredentialVault envelope before persistence. The envelope uses randomized data keys and authenticated identity binding for owner, provider, account, credential type, record, scope, revision and key identity. Private backend consumers open plaintext only inside the narrow adapter boundary. Browser code has no new-secret local writer or general reveal/copy API. Legacy browser imports require explicit selection, password and consent, and local cleanup happens only after a successful server-vault write.

Focused tests cover wrong-owner substitution, ciphertext and metadata tampering, rotation, revocation, PKCE TTL and one-use behavior, idempotent migration, concurrent revoke and production refusal of development crypto. The credential source audit retains 117 candidates in 37 semantic groups and seven canonical static vault importers. The seventh importer validates runtime persistence receipts without opening plaintext. Legacy reads are denied on production hosts unless the explicit bounded migration window is enabled.

Google Cloud KMS is the selected compatible managed-provider adapter. It uses Application Default Credentials, an exact CryptoKey resource, provider-side envelope-key wrapping and the record identity as additional authenticated data. Focused transport tests prove exact key and AAD binding, malformed-response rejection, wrong-key rejection and 32-byte data-key enforcement. Production and unknown runtimes still fail closed without this managed configuration.

The managed key has not been provisioned or verified because Google Cloud requires a billing-enabled project and usage can incur charges. Phase 3 cannot be declared fully verified until the founder separately authorizes account and IAM setup, then the isolated cutover test supplies genuine provider receipts.
