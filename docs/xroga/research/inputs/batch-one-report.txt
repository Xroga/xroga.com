Xroga OS Batch One — Backend Foundation, Security, and Execution Truth
Executive implementation decision
Batch One should not attempt to bolt ten new feature systems onto Xroga. Its job is to make the existing platform trustworthy enough that the remaining ninety implementation commands can safely build on it.

The live repository audit shows that Xroga already contains important primitives worth preserving: authenticated backend routing, Supabase integration, an existing migration mechanism, business-action planning and approval concepts, CI workflows, publishing services, and integration infrastructure. For example, backend authentication is already centralised through backend/src/middleware/auth.ts, and protected routes are mounted through that middleware in backend/src/index.ts. The repository also already contains Supabase administration/configuration and migration tooling rather than needing a new database layer.

Likewise, Xroga should extend rather than discard its current authority model. operationsEngine.ts already contains digest-bound confirmation/approval concepts, while businessAction.ts already implements a prepared business-action plan and digest-based authorisation boundary.

One area that deserves genuine replacement/hardening is credential persistence. The current oauthPkceStore.ts visibly persists OAuth credential material into database/storage fields; application-layer envelope encryption is not visible in that module. Batch One therefore replaces that persistence boundary while keeping the higher-level integration APIs compatible.

The repository already contains numerous CI workflows, so the correct move is to consolidate and make them deterministic rather than create another independent CI universe. AGENTS.md also already exists and should be strengthened rather than replaced.

The supplied Xroga source bundle identifies 119 feature/evidence requirements and the earlier implementation programme identifies 72 original missions. Batch One establishes the truth, security, reproducibility and acceptance infrastructure underneath all of those requirements.

The shared ChatGPT URL was not independently retrievable in this research environment. Therefore Command 002 explicitly requires the coding agent to reconcile the supplied exported research bundle and mark any still-inaccessible share content as INACCESSIBLE_PENDING_EXPORT rather than inventing requirements.

Batch completion state and boundaries
After these ten commands, Xroga is not yet “fully finished.” What should be finished is the layer that makes the remaining product work safe and measurable:

Truth becomes canonical. Xroga will know what code really exists and what remains partial.

Research becomes traceable. None of the 119 discovered requirements or prioritised repositories should disappear between prompts.

Builds become reproducible. Later commands cannot hide broken code behind environment-specific behaviour.

Infrastructure becomes explicit. Future agents stop guessing where API, workers, queues, storage and deployment actually live.

User promises become executable tests. Chat, research, coding, business actions, workflows, AI Employees, Android publishing and mixed requests all get stable acceptance contracts even where later implementation remains.

Tenant isolation becomes a backend invariant. A resource identifier is never treated as sufficient ownership proof.

Approval becomes precise authority. The action actually executed must be the action the user authorised.

Credentials become backend secrets rather than general application data.

Tool and network access becomes policy-controlled. A webpage, uploaded document, MCP description or model output cannot promote itself into permission.

The major information still genuinely unspecified after research is the production key-management provider that should back Command 009; Command 004 must resolve Xroga's actual hosting/KMS options first. Pact JS’s pinned licence should also be independently checked before introducing it as a dependency. The shared ChatGPT page itself was not directly retrievable in this research environment, so Command 002 correctly treats its exported Xroga source bundle as available evidence and the original page as pending export rather than fabricating access.

Most importantly, Batch One deliberately does not replace Xroga's current AI/execution system simply because replacement is allowed. It creates the benchmarks, security boundaries and evidence needed to make that decision intelligently. If a later planner, compiler, workflow engine or agent runtime demonstrably beats Xroga’s current system against the golden journeys while preserving durable execution, tenant boundaries, authority, cost limits and verification, then a later command can replace the weaker component with an evidence-backed migration. That is the safer route to the highly autonomous Xroga SI product you are targeting than replacing architecture before Xroga has a trustworthy way to measure whether the replacement is actually better.
