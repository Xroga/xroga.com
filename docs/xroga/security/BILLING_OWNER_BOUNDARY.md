# Billing ownership review

Candidate extends the existing BillingService, webhook delivery table and fulfillment transaction. No new ledger, provider or scheduler. Production billing is unchanged until separately approved release.

Confirmed defects: syncMembership accepted metadata ownership for a globally keyed membership and merge-upserted user_id. The fulfillment RPC preserved user_id on conflict but changed an existing foreign membership after granting the supplied actor an entitlement. Failed webhook retry checked only SQL errors, so a zero-row race could still process. Catch handling copied arbitrary exception text into logs and safe_error.

Corrections: compare metadata to persisted membership ownership; insert-ignore then update by membership ID AND owner with one returned row; fulfillment's conditional conflict update raises on foreign ownership so the whole transaction rolls back; payment-ID duplicates must also belong to the actor. A retry proceeds only after one claimed row. Failure classification uses fixed codes. Existing legitimate same-owner renewal, duplicate receipt, plan, account, price and allowance contracts remain intact.

The migration replaces only fulfill_whop_payment with the same signature and service_role-only grants, adds no table/column, removes no data and retains the original user advisory lock. The unique membership conflict serializes concurrent inserts; its owner predicate is evaluated atomically. Failure after entitlement statements rolls back all preceding writes. NULL account/plan/date evidence now fails explicitly. All70 migration files must pass fresh, sanitized representative upgrade and reapply before consideration for staged rollout.

Verification: existing12 BillingService assertions retained, plus actual SDK transport ownership/race test. New loopback HTTP test verifies invalid HMAC, lost/won retry claims and failure redaction. Two new real disposable Supabase tests exercise same-owner updates, foreign denial, competing member creation, full transactional rollback, browser RPC denial and same/foreign payment replay. These are isolated synthetic payment records, no Whop API or charges. Final-source real execution pending; unit fixtures alone do not satisfy database acceptance.

Remaining gaps: first membership/payment binding relies on signed provider metadata from server-created checkout; no durable local checkout binding exists. Actual provider renewal variants and staged compatibility are unverified. Completion-store write failures and process crash recovery need further review. None is silently waived by the HMAC or new predicates. Full Command007 and Commands008–010 remain incomplete.

Rollout: draft PR only; no production migration or provider call. Validate full chain, owner/race/rollback cases, aggregate tests and authorized staging before release. If a regression occurs after an approved staged rollout, stop callback processing through the existing deployment rollback process; retain records and restrictive owner guards. Reverting to the old unsafe function requires a separately reviewed corrective migration, never automatic removal of ownership protection or deletion of receipts. No database rollback is executed here.
