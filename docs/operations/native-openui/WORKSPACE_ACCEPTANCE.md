## Release and rollback

1. Pass exact-source CI, including the ordinary-user browser test in `command3-auth.spec.ts`. It uses real isolated accounts, browser input, clipboard, share routes and storage with synthetic planner and response endpoints. Separate provider-transport tests exercise native file and approved-research flows through canonical settlement. Neither check spends provider tokens or substitutes for live staging.
2. For the next hosted gate, pin one source for the API and frontend and verify both release endpoints. Use the existing private isolated staging service, issuer and ledger with zero default traffic to the candidate. Keep evaluator configuration unset. Use ordinary authenticated test accounts. Enable `XROGA_NATIVE_OPENUI_WORKSPACE=1` only on the candidate and prove the previous staging traffic target and secret permissions can be restored.
3. Before a separately authorized paid attempt, set enforceable per-account reservation/spend ceilings and count the semantic planner, the answer and any research dispatch. Confirm CORS, ordinary-user login, invalid bearer denial, private Share and file access for two accounts before admitting inference. Bind the existing provider secret only to the isolated candidate, with an expiry. Stop on an unexpected request, authorization failure or unsettled receipt. The four earlier approved slots are consumed.
4. Exercise the two corrected benchmark prompts and a native attachment-backed response in the normal composer. Verify actual provider/ledger receipts, expected fallback and cancellation semantics, UI interaction without new charges, history reopening and cross-account denial. Use replay or fixture evidence for the wider component and viewport matrix. If current-source retrieval requires an extra paid call or permission, keep it outside the capped run unless explicitly included. Restore the prior staging revision and remove temporary access at the end.
5. Only after live acceptance, recheck the deployed production frontend, API and canonical Job sources and obtain the paired release decision. Deploy the compatible renderer and restore path before enabling native generation. Monitor fallback, user-reported render errors, latency and ledger integrity during the canary. Do not remove legacy presentation or historical decoders during the same cutover.
6. Roll back by disabling the presentation flag or restoring the previously verified paired release. Keep the new client compatible with native saved responses already produced, and preserve existing history and access checks. Do not remove the older presentation implementation before real canary and historical-compatibility acceptance.
