## The browser worker image (`deploy/browser-worker/`)
| Mandatory property | Mechanism | Evidence |
|---|---|---|
| separate, restricted image | its own `Dockerfile`; base `mcr.microsoft.com/playwright:v1.62.0-noble` pinned by **digest** (`sha256:baed2032…`); `playwright-core@1.62.0` locked by `package-lock.json`, installed with `npm ci --ignore-scripts` | built and run locally |
| non-root | numeric `10001:10001`, no home, no login shell | `containerSpec` + Dockerfile checks; the probe reports `uid 10001` |
| Chromium sandbox ON, else BLOCKED, never `--no-sandbox` | `chromiumLaunch.ts` sets `chromiumSandbox: true` explicitly (**Playwright defaults it to false, which silently adds `--no-sandbox`**) and refuses anything weaker; the probe never relaxes anything and exits non-zero when it cannot establish the sandbox | **DOCKER_LOCAL_TESTED (Docker Desktop, linux/amd64, kernel 6.18 WSL2, not OCI)**: `SANDBOX_ON`, every Chromium process (browser, zygote, GPU, utility, renderer) seccomp-filtered, renderer in its own PID namespace, no `--no-sandbox` on any command line. **Control with Docker's default seccomp profile: `BLOCKED` ("Chromium sandboxing failed!")**, so the probe can say no and the derived profile is what enables the sandbox |
| seccomp, dropped capabilities | `seccomp-chromium.json` = Docker's default plus **exactly** `clone`, `clone3`, `unshare`, `setns`, `chroot` (derived by `derive-seccomp.mjs` from the pinned upstream file; `--check` re-derives and compares). `capDrop: ALL`, `capAdd: []`, `no-new-privileges`. Discovered by running, not assumed: without `chroot` Chromium fails with `Check failed: sys_chroot("/proc/self/fdinfo/")` | probe run; `containerSpec.test.ts` pins the profile to default-plus-five and checks that no capability-gated syscall was opened |
| no privileged mode, no Docker socket, no host namespaces or mounts, no published port | `container-spec.json`, tmpfs-only mounts (`nosuid,nodev,noexec`, sized), `ipc/pid/uts private`, bridge or none network | `assertContainerSpecSafe` refuses each one (28 mutations in the test) and `dockerRunArgs` turns the spec into the exact `docker run` flags the probe used |
| CPU / RAM / process limits | 2 CPU, 2048 MB with swap equal to memory, 512 pids, 256 MB shm | enforced by the spec checker with ceilings |
| private authenticated CDP | no TCP DevTools port or address is accepted; Playwright talks over `--remote-debugging-pipe` | launch checker + **real Chromium**: the live process command line has the pipe flag and no debugging port |
| egress policy: metadata, RFC1918, loopback, rebinding | `egressProxy.ts` in front of the browser (`--proxy-server`, `<-loopback>` so localhost goes through it too): per-job credential, 443 only, host must be in the job's allowed origins, then the canonical policy (`security/boundedPublicGet.ts`, extracted unchanged from Batch 1): one DNS resolution, every answer public, connection pinned to that answer | LOCAL_TESTED, 13 proxy tests; **real Chromium**: out-of-scope host refused before any DNS, 127.0.0.1 / localhost / [::1] and a live internal service never reached, cloud metadata unreachable, an in-scope host with an untrusted certificate fails in the browser (TLS errors are never ignored). Finding from the real run: Chromium cannot authenticate to a 407 without a `Proxy-Authenticate` header; fixed and pinned by a test. 6 + 1 injected defects caught |
| per-tenant temporary profiles | `buildChromiumLaunch`: one directory per hash of (tenant, run, task, attempt) under a fixed root; identifiers never appear in a path; downloads inside the profile | LOCAL_TESTED |
| process-tree cleanup | `processTree.ts` | see INFRA-006 |
| network-level egress rules that hold even if the browser were compromised | **declared, not verified**: the spec requires `egress.enforcement = required-at-deploy` and a deny list of every private, loopback, link-local (metadata), CGNAT and benchmarking range; the checker refuses a spec without it. Enforcing it (security list / firewall) happens on the host that runs the container | NOT VERIFIED: needs the host (D2/D3) |
| AMD64 and ARM64 proof before choosing a shape | AMD64 proven locally. The base image is multi-architecture and the probe is the same command on any host | **ARM64: NOT RUN** (no ARM64 host available here). **OCI host: NOT RUN.** Neither is claimed |
| pinned Stagehand | not applicable yet: there is no Stagehand dependency in the repository; local-mode Stagehand is INFRA-007 (Phase 3) | NOT STARTED |

## Reproduce
```
docker build -t xroga-browser-worker:phase2-probe deploy/browser-worker
npx tsx scripts/browser/run-sandbox-probe.mts --out <file>           # hardened run + control run, writes the evidence record
node deploy/browser-worker/derive-seccomp.mjs --check                # the profile is exactly its derivation
```
On the target host, run the probe with `--label OCI_HOST_TESTED`: until that run exists, the claim "Chromium can run sandboxed on OCI" is not made.

## Residual risks, stated
- The profile permits `clone`, `clone3`, `unshare`, `setns` and `chroot` without a capability. The kernel still checks each against the caller's capabilities, so with every capability dropped they work only against the user namespace the sandbox creates for itself. This enlarges the kernel surface exposed to the browser (user namespaces); it is the cost of running Chromium's sandbox in a container without `CAP_SYS_ADMIN`, and the alternative is a VM per job. It is a decision for the founder, not a silent default.
- The egress proxy is application-level. A browser compromise that escapes the renderer sandbox could still open its own sockets; the deployment-level deny rules above are what stop that, and they are unverified.
- Docker Desktop's LinuxKit kernel is not an OCI Ampere or AMD shape. Kernel settings (`user.max_user_namespaces`, AppArmor policy on the host) can differ.
