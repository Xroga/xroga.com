# Batch 1.5 audit and hardening (2026-10-26)

Branch `claude/batch15-audit-fixes`, from `main` at `bc669f8a` (the PR #852 merge). Draft, not for merge or deploy. Nothing here touches Codex's migration branch or a production resource.

Method: the three Batch 1.5 specifications were re-read and compared to the code on `main`; the integration merge was diffed against the pre-merge Phase 3 branch (`claude/xroga-b15-phase3-20261024`). Every finding below was confirmed in code before it was changed. Evidence labels: **FIXED + TESTED** (regression test added), **DEFERRED BY DESIGN** (an explicit, documented decision this audit respects), **OPEN** (needs the Google cutover or a product decision).

## Findings and resolutions

| # | Finding | Severity | Resolution |
|---|---|---|---|
| 1 | `POST /api/browser/runs` accepted a client-supplied `plan.writeGrant`. `parseBrowserPlan` accepts any string of the right shape as a grant and nothing looked it up, so a client could authorise its own consequential `submit` and `upload` steps. Only the model planner stripped the field | High (authorization) | **FIXED + TESTED.** The route refuses any request whose plan carries a `writeGrant` (400 `RUN_INVALID`) before anything is parsed, stored or run. Grants remain issuable only by the server's canonical action-grant path. `browserRuns.test.ts` |
| 2 | `guestClientAddress` trusted `fly-client-ip` unconditionally and `trust proxy` is not set. Behind Cloud Run a caller can send that header and rotate it to evade the guest rate limit; without it every guest shares Google's frontend address | Medium (abuse, Google cutover) | **FIXED + TESTED.** A header is trusted only where the platform sets it: Fly (`FLY_APP_NAME`) trusts `fly-client-ip`; Cloud Run (`K_SERVICE`) takes the last `X-Forwarded-For` entry (the one Google appended; `XROGA_TRUSTED_PROXY_HOPS` for extra trusted hops); anywhere else the socket address is used. `guestChat.test.ts` |
| 3 | Browser-run `workerId` was `api-${FLY_MACHINE_ID ?? process.pid}`: every Cloud Run container has pid 1, so all instances shared one id in lease diagnostics | Low | **FIXED.** Per-process unique (`K_REVISION` or Fly machine id plus a random suffix) |
| 4 | `getStorageService()` and the browser-runs deps cached `null` for the life of the process after one transient failure, so a cold start before a secret or Drive was ready left Drive and browser runs returning 503 until restart | Medium (availability) | **FIXED.** Failures and "not configured yet" are not cached; only a successfully built service is |
| 5 | Drive reservation sweep, abandoned-upload cleanup, interrupted-deletion completion and re-verification ran only from an operator script. Nothing scheduled them, so bytes reserved by abandoned uploads stayed reserved | Medium | **FIXED + TESTED.** `POST /internal/storage/reconcile`: Google-signed ID token for one named service account and audience (the same verifier as the automation tick), off unless `XROGA_STORAGE_RECONCILE_MODE=cloud`, bounded (200 per call, never scans the whole bucket), counts only in the response. `storageReconcileScheduler.test.ts` |
| 6 | Cloud Run was "unclassified" with no explanation and production could be claimed by a service named `...-staging` | Medium (cutover) | **FIXED + TESTED** in `runtime/startupPolicy.ts`: a clear problem message for Cloud Run, and a Cloud Run service whose own name says staging, preview, sandbox, dev or test cannot declare itself production. The module is still not wired (see 7) |
| 7 | The startup policy (`decideStartup`) and the readiness evaluator (`runReadiness`, `apiProbes`) are not wired into `index.ts`; `/ready` checks only the credential vault and the database; boot reconciles orphaned runs in every environment | High as an acceptance gap, but **DEFERRED BY DESIGN** | The integration merge removed the Phase 2 wiring on purpose and `runtime/bootGuard.test.ts` pins that: the evaluators "recognise production only by the Fly app name, so wiring them is part of the Google Cloud cutover (DEPLOYMENT-HOLD.md)". That decision is respected. With finding 6 the policy now recognises Cloud Run, so the wiring is ready. The exact, tested change is saved as `docs/infra/batch-1.5/cutover-startup-readiness.patch` and must be applied, with `bootGuard.test.ts` updated, in the cutover release |
| 8 | Browser runs executed in the HTTP request's process after the 202 response; the cancel map and admission limits were per process; the production store could not checkpoint at all | High for Cloud Run | **FIXED + TESTED (code); Google runtime verification PENDING.** A run is a durable record (`browser_runs`: spec, canonical state, cancel flag). `POST` validates and stores it, then a dispatcher hands the id to a worker (in-process, or Cloud Tasks calling the signed `POST /internal/browser/execute`). Any instance can execute, cancel (`DELETE` sets a durable flag the runner polls) or recover (`POST /internal/browser/recover`, lease-aware) a run; an execution lease admits one executor; the per-tenant ceiling is counted from the shared table. Also fixes a defect found on the way: the route built `SupabaseExecutionStateStore` without a swarm attempt, whose `save` always refuses, so no production run could persist. `browserRunDurability.test.ts`, `browserRunDispatch.test.ts`, `browserRunInternal.test.ts`, `browserRunStore.integration.test.ts` (real PostgreSQL in CI). See `DURABILITY-AND-DRIVE-UI.md` |
| 9 | There is no frontend for Xroga Drive | Product gap | **BUILT (new scope, not a Batch 1.5 requirement: the three specifications describe the API, storage and worker, not a Drive screen).** `/drive` behind `NEXT_PUBLIC_XROGA_DRIVE=1`: list, upload (single and multipart, signed URLs, retries, cancel), download, delete, honest states. Client and routes are pinned by `driveApiContract.test.ts`; the uploader by `driveUpload.test.ts`. Browser to R2 transfer needs bucket CORS (PENDING, real R2) |
| 10 | Quota is not enforced by default: `STORAGE_QUOTA_BYTES` unset means no quota check | By design | **Default kept (deliberate, documented); misconfiguration closed.** A value that was set but not a whole number (for example `10GB`) used to be read as "no limit" silently. It is now a startup and readiness problem and Drive stays unavailable until corrected. Readiness reports `storage_quota_not_enforced` and `storage_reconcile_not_scheduled` (non-blocking) so an unlimited or unscheduled deployment is visible. The number itself is a product decision for activation. `quotaConfig.test.ts`, `readiness.test.ts` |
| 11 | `storage-phase1.yml` (real PostgreSQL and S3 emulator) runs only on listed branch pushes and not on `main` or PRs, by design | Process | The audit branch is added to its list so the integration tests run on it |
| 12 | Browser worker coordinator replay cache is in memory and the secret has no rotation | Low, **OPEN** | Accept two secrets for rotation and refuse requests for a short period after start; schedule with the cutover |
| 13 | A deleted project's Drive objects remain as the owner's project-less objects and keep counting toward quota (`on delete set null`) | Product decision, **OPEN** | Confirm intended |
| 14 | `browserRuns.ts` builds a second `pg.Pool` for leases (up to 16 connections per instance against the Supabase pooler) | Low, **OPEN** | Share the storage pool with the cutover |
